### <a name="_3bfxc9a45514"></a>**Функциональные требования**

|**№**|**Действующие лица или системы**|**Use Case**|**Описание**|
| :-: | :- | :- | :- |
| 1 | Покупатель, Mobile App | Просмотр списка заказов | Покупатель открывает личный кабинет. Система возвращает список всех заказов: сумма, дата, способ доставки, финальный статус. |
| 2 | Покупатель, Mobile App | Просмотр деталей заказа | Покупатель открывает конкретный заказ. Система возвращает: список товаров, количество, цену, итоговую сумму, способ доставки и оплаты, финальный статус. |

### <a name="_u8xz25hbrgql"></a>**Нефункциональные требования**

|**№**|**Требование**|
| :-: | :- |
| 1 | Отклик интерфейса истории заказов ≤ 0,3 с в 98% случаев и ≤ 1 с в 99,99% случаев. |
| 2 | Read-модель должна быть изолирована от write-side: нагрузка на чтение истории не влияет на оформление заказов. |
| 3 | Система должна выдерживать рост до 40 000+ заказов/день без пересмотра архитектуры чтения. |
| 4 | При добавлении новых полей в историю (например, трек-номер) не должно требоваться изменения Order Service. |
| 5 | Данные истории должны быть согласованы с финальным состоянием заказа (доставлен / отменён). |

### <a name="_qmphm5d6rvi3"></a>**Решение**

**Выбранный паттерн: CQRS с Event Sourcing на write-side (частично).**

Архитектурное решение:

1. **Write-side остаётся как в Task1.** Order Service, Payment Service, Delivery Service публикуют доменные события в Event Bus (`OrderCreated`, `PaymentSucceeded`, `OrderConfirmed`, `DeliveryScheduled`, `OrderCancelled`, `RefundSucceeded`). Order DB хранит актуальное состояние заказа для транзакционных операций.

2. **Добавляется Order History Projection.** Это consumer, который подписывается на события из Event Bus и обновляет денормализованную таблицу в Order History DB. Каждая строка — один заказ с уже собранными полями: `order_id`, `customer_id`, `total_amount`, `created_at`, `delivery_method`, `payment_method`, `final_status`, `items_json`, `tracking_number`, `receipt_url`. Проекция идемпотентна (повторная обработка события не создаёт аномалий).

3. **Добавляется Order History Query Service.** Лёгкий сервис, который читает только Order History DB и отдаёт готовый DTO для мобильного приложения. Никаких синхронных вызовов других сервисов.

4. **Event Sourcing применяется частично.** События в Event Bus — источник истины для проекции. Order DB на write-side остаётся state-based (не полный Event Sourcing с event store для каждого агрегата), но история изменений заказа фиксируется в событиях. Этого достаточно для сценария истории без усложнения MVP.

**Почему решение удовлетворяет требованиям:**

- **Отклик.** Запрос истории — один `SELECT` из денормализованной таблицы (с пагинацией). Время ответа определяется только Order History DB, оптимизированной под чтение и не конкурирующей с транзакциями оформления заказа. Укладывается в 0,3 с.
- **Изоляция.** Чтение истории не затрагивает Order Service, Payment Service, Delivery Service. Всплеск запросов истории не влияет на оформление новых заказов.
- **Расширяемость.** Добавление нового поля в историю требует изменения только Projection и схемы Order History DB. Order Service не меняется.
- **Масштабирование.** Projection и Query Service масштабируются горизонтально независимо от write-side. Event Bus (Kafka) партиционируется по `customer_id` или `order_id`, что позволяет обрабатывать 40k+ заказов/день.

Диаграмма контейнеров (C4) для обновлённой архитектуры вынесена в отдельный файл `c4-container-task2.puml` в директории `Task2`.

### <a name="_bjrr7veeh80c"></a>**Альтернативы**

| Альтернатива | Плюсы | Минусы | Почему не выбрана |
|:-|:-|:-|:-|
| **API Composition** (шлюз или отдельный сервис синхронно вызывает Order Service, Payment Service, Delivery Service и собирает ответ) | Простота реализации; не нужна отдельная БД; данные всегда «свежие» | Каждый запрос истории = 3+ синхронных вызова. Задержка складывается из времени ответа всех сервисов. При пиковых нагрузках каскадные задержки, отказ одного сервиса обрушивает сценарий. Не укладывается в 0,3 с. | Нарушает NFR по отклику и изоляции. |
| **Полный Event Sourcing** (event store для каждого агрегата, восстановление состояния из событий при каждом запросе) | Максимальная прослеживаемость; полная история изменений | Восстановление состояния из событий при каждом чтении медленно. Требует снапшотов и усложняет инфраструктуру. Избыточно для MVP. | Избыточная сложность; не даёт выигрыша в отклике по сравнению с проекцией. |
| **CQRS без Event Sourcing** (проекция обновляется прямыми вызовами из Order Service через API или outbox-таблицу без событийной шины) | Проще, чем с Event Bus | Связывает Projection с внутренним API Order Service; нарушает EDA-принципы из Task1. Добавление новых источников (Payment, Delivery) потребует отдельных интеграций. | Противоречит выбранной в Task1 событийной архитектуре. |

**Недостатки, ограничения, риски**

| Риск / ограничение | Описание | Митигация |
|:-|:-|:-|
| **Eventual consistency** | История может отставать от актуального состояния заказа на секунды (пока событие дойдёт до Projection). | Для сценария «история покупок» приемлемо: покупатель смотрит завершённые заказы. В UI можно показывать статус «обновляется» для самых свежих заказов. |
| **Дублирование данных** | Order History DB хранит денормализованную копию данных из Order DB, Payment DB, Delivery DB. | Осознанный trade-off: дублирование в обмен на скорость чтения. Проекция идемпотентна. |
| **Сложность обработки ошибок проекции** | Если Projection упадёт или пропустит событие, история будет неполной. | Kafka хранит события с retention; Projection перечитывает поток с нужного offset. Алерт на consumer lag. |
| **Версионирование схемы событий** | Изменение структуры события требует совместимости старой и новой версии в Projection. | Schema registry (Confluent Schema Registry) или явное поле `version` в каждом событии. Projection обрабатывает обе версии. |
| **Event Sourcing только частично** | Order DB не является event store; полная история изменений заказа не восстанавливается из событий на write-side. | Для сценария истории покупок достаточно. При необходимости полного аудита можно добавить event store для Order Service без изменения read-side. |
